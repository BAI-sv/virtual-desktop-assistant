# 排障手册

> 这里每一条都在**真机上复现过**，按「现象 → 根因 → 解法」写。
> 没有一条是想象出来的。

## 1. 完全没声音 / 声音跑到蓝牙耳机里去了

**现象**：球在跑、日志显示它一直在说话，但用户一个字都听不见。

**根因**：
**只要某个程序用了蓝牙耳机的麦克风，Windows 就会把「默认播放设备」也切到那个耳机**
（蓝牙免提 HFP 模式的连带行为）。而这个切换**在程序退出后不会自动还原**。

```
实测现场：
  [fairy] 语音=克隆路由(indextts-clone) 889388 字节   <- 球确实在说话
  [fairy] 播放 fairy_say.wav
  但默认输出 = 耳机 (蓝牙 Hands-Free AG Audio)        <- 声音全进耳机了
```

**解法**：

```bat
py -3.12 <FAIRY_ROOT>\tools\fairy_audio.py current              :: 现在默认是哪台
py -3.12 <FAIRY_ROOT>\tools\fairy_audio.py list                 :: 有哪些可选
py -3.12 <FAIRY_ROOT>\tools\fairy_audio.py set 扬声器            :: 切走（名称片段匹配）
py -3.12 <FAIRY_ROOT>\tools\fairy_audio.py save                 :: 记成"已知正常"
```

**根治**：凡是要用蓝牙麦克风的程序，**启动前 `save()`、退出时 `restore()`**。
`fairy_audio.py guard-on` 就是干这个的（保存 + 进程退出时自动还原）。

> ★ **附带一条硬约束**：**必须只对「激活中」的设备切换**。
> 切给一个未激活的设备（比如已经断开但还留在列表里的蓝牙音箱），
> `SetDefaultEndpoint` 会返回 `hr=0`（成功）但**实际不生效**，Windows 静默退回原设备。
> 这就是 `list` 要分「激活中 / 全部」两段显示的原因。

## 2. 说话变成"通用音色"了，不是目标音色

**现象**：声音还是中文、也能听懂，但音色完全不对（像导航播报）。

**根因**：合成服务（IndexTTS `:9881`）挂了，球降级到 Edge TTS。

**怎么确认**（★ **别用 `edge` 关键字搜日志**）：

```bat
py -3.12 <FAIRY_ROOT>\tools\voice_audit.py
```
看 `EDGE (.mp3)` 这一行 —— **不为 0 就说明发生过降级**。
或直接搜日志里的 `fairy_say.mp3`（`.mp3` 就是 Edge 的指纹）。

**解法**：

```bat
py -3.12 <FAIRY_ROOT>\tools\fairy.py start tts                    :: 手动起合成服务（约 35 秒）
py -3.12 <FAIRY_ROOT>\tools\indextts_guard.py --status-json       :: 确认在不在
py -3.12 <FAIRY_ROOT>\tools\fairy.py start guard                  :: 起保活守护（以后自动救）
```

**为什么 Edge 会存在**：它是最后一道保险 —— **宁可音色不对，也不能哑巴**。
所以它的优先级最低，正常情况永远轮不到它。

## 3. 重启后第一句话要等十几秒

**现象**：球起来了，你说话，它卡 15~25 秒才出声。

**根因**：**冷启动**。合成服务第一次推理要做 JIT 编译 + 显存分配。

```
实测：首次合成 15.50 秒（冷）  ->  之后 2.9 ~ 5.3 秒（热）
```

**解法**：让服务**起来后立刻暖机**（合成一句废话丢掉）。

`indextts_guard.py` 已实现：拉起成功且 `loaded=true` 后会暖机，
并把耗时记到状态文件的 `warmup_s` 字段。

**手动暖机**：

```bat
py -3.12 <FAIRY_ROOT>\tools\indextts_guard.py --once
```
或者随便打一次 `POST /tts` 预热。

> 暖机失败**不算启动失败** —— 不能因为暖机报错就去重启服务。

## 4. 球像"哑巴"：日志文件是空的 / 完全没日志

**现象**：球明明在跑、也在说话，但日志文件停在很久以前，一行新内容都没有。

**根因**：球默认用 **`pythonw.exe`（无控制台）** 跑。
**`pythonw` 的 stdout 没有接收方 —— 所有 `print()` 直接被丢弃。**
你把输出重定向到文件才有日志，不重定向就什么都没有。

**解法**：**用总管启动**，它会接管 stdout：

```bat
py -3.12 <FAIRY_ROOT>\tools\fairy.py start ball
```

`fairy.py` 的 `start_one()` 会做 `open(LOG + script + ".log", "ab")` 当 stdout，
所以日志落在（见 `tools/fairy.py` 顶部的 `LOG` 常量）：
`<WORKDIR>\logs\fairy_ball.py.log`

**注意**：**日志目录是硬编码在工作目录里的**。
如果你的部署路径不同，要么改 `LOG` 常量，要么自己在启动时重定向。

## 5. 麦克风打不开（`Errno -9999`）

**现象**：用 `sounddevice` 打开某个输入设备，报 `PortAudioError ... -9999`。

**根因**：本机多个输入设备是 **WDM-KS** 后端，**打开一律失败**：

```
实测（本机）：
  ✗ 麦克风 (Realtek HD Audio Mic input)       全部 -9999 打不开
  ✗ 线路输入 (Realtek HD Audio Line input)    全部 -9999 打不开
  ✗ 耳机 (@System32\drivers\bthhfenum.sys...)  全部 -9999 打不开
  ✓ 耳机 (蓝牙 Hands-Free AG Audio)            能打开 @16000Hz
  ✓ 立体声混音 (Realtek)                       能打开 @192000Hz  ← 但它是回环，不能用
```

**解法/结论**：
1. **不能只看名字判断"能不能用"** —— 名字里有"麦克风"不代表能打开。
   **必须真去开一次**（`mic_watch.py` 就是这么做的：逐个试开）。
2. **唯一可用的真麦克风**可能是蓝牙耳麦（或你插的 USB 麦）。
3. **千万不要用"立体声混音"当输入** —— 它是**回环设备**，
   会把系统播放的声音录回去，**导致 AI 听见自己说话，变成自言自语**。

**相关工具**：

```bat
py -3.12 <FAIRY_ROOT>\tools\mic_watch.py --once        :: 探一次，列出真正能用的麦克风
py -3.12 <FAIRY_ROOT>\tools\mic_watch.py --list        :: （等价）看设备清单
py -3.12 <FAIRY_ROOT>\tools\fairy_ear.py --list        :: 耳朵视角的设备清单
```

## 6. 蓝牙耳麦占用时，同一副耳机放不出声音

**现象**：一边用耳麦听唤醒词，一边想往同一副耳机播声音 —— **播放超时/失败**。

**根因**：**HFP（免提）和 A2DP（立体声）不能同时用在同一副蓝牙耳机上。**
麦克风一被占用，链路就切到 HFP，**A2DP 输出被堵**。

**结论**：**"边听边说"在单副蓝牙耳机上基本行不通。**

**解法**：
- 用蓝牙耳机当**麦克风**，用**别的设备**（音箱 / 显示器扬声器）当输出；
- 或者用**有线/USB 麦克风** + 蓝牙耳机当输出。

## 7. 唤醒词喊了没反应

**排查顺序**（**别跳步**）：

```
① 先确认【真的有程序在听】—— 这是最常见的"根因"
   py -3.12 <FAIRY_ROOT>\tools\fairy_wake_listen.py 120
   如果它都没在跑，你等于对着一台关着的麦克风喊。

② 看麦克风音量有没有上来（脚本每 3 秒打一行）
   [ 3.1s] LVL max RMS over 3s = 0.05838   有声音   <- 好
   [ 6.2s] LVL max RMS over 3s = 0.00004   很安静   <- 麦克风问题

③ 有声音但没命中 -> 是"词"或"门限"的问题
   · 中文模型对英文部分很弱：「你好Fairy」这种中英混读最难
   · 改喊纯中文（"你好飞瑞"）或纯英文（"Fairy"）
   · 门限 keywords_threshold 从 0.10 降到 0.05

④ 还是不行 -> 见 docs/wakeword.md 的两个坑
   ★ 最重要的是：音频必须【流式喂】（每 0.1 秒一块），整段喂永远不中
```

## 9. 日志停在"门限通过"，后面什么都没有

**现象**：唤醒程序打了 `门限通过` 之后，就再没有任何输出，程序看着像死了。

**根因（两个，叠在一起）**：

```
① 【取整精度不够】
   代码把音量【乘 1000 再取整】比较：
       门限 0.006  -> int(6)    用户说话 0.00475 -> int(4)   4 < 6  -> 永远过不去 ✗
       门限 0.0008 -> int(0.8)=0   连静音 int(0.00004*1000)=0 也通过 ✗
   → 两端都是同一个 bug：分辨率只有 0.001，门限低于它就没意义
   解法：乘 100000（分辨率 0.00001）

② 【模型加载是懒加载的】
   第一次触发才去加载模型，而模型加载要 63 秒，
   期间【一个字都不输出】-> 看起来完全卡死
   解法：进循环前先加载好，并明确打印"正在加载模型"
```

**教训**：**"看着像死了"往往只是"它在闷头干活但没有输出"。**
**关键路径上必须打印进度**，否则排障无从下手。

## 10. 唤醒引擎"结果乱跳"（0/2 ~ 2/2 不稳定）

**根因**：**喂音频的方式错了** —— 整段喂而不是流式喂。

**解法**：见 [`wakeword.md`](wakeword.md) 坑 1。
同一段音频，整段喂 3 次全不中，流式喂 3 次全中，**可复现**。

## 11. 用合成音频（TTS）自测唤醒 —— 得出错误结论

**现象**：拿 `edge-tts` 合成的 "Fairy" 去喂唤醒引擎，几乎不中，
于是以为"模型不行"。

**根因**：**这些 KWS 模型只认真人说话的嗓音特征，不认 TTS 合成音。**
```
实测：7 条 TTS 合成只中 1 条；真人/游戏原声 9~10/12
```

**解法**：**验证唤醒必须让人真喊**（或者用真人录的音频）。
拿合成音自测会得出完全错误的结论。

## 12. 中文引号写进代码 -> `SyntaxError`

**现象**：
```
File "<stdin>", line 15
    print("检查“设备插拔”模块")
          ^
SyntaxError: invalid syntax. Perhaps you forgot a comma?
```

**根因**：**中文引号（`“ ”`）跟英文引号长得像但不是同一个字符**，
写进 Python 字符串里就直接把字符串截断了。

**解法（机械规则）**：
```
代码里的字符串外层用 '...' 或 "..."
正文里要引号 —— 一律用「」（或『』）
★ 绝不在代码字符串里出现中文引号
```

**这不是小事**：这个坑一天之内就触发了 **10 次以上**。
**"我记得要小心"是没用的，必须变成写代码时的固定动作。**

## 14. 安装/卸载音频驱动后没生效

**现象**：`pnputil` 报 `System reboot is needed to complete install operations`，重启后还是老样子。

**根因/注意**：
```
· 驱动安装【确实需要重启】才能真正生效
· 重启后，把设备【移除再扫描】，Windows 可能装回【驱动库里更老的版本】
  实测：删掉 6.0.9492.1 后扫描，装回来的是 6.0.8975.1（2020 年的）
  解法：从备份重新装较新的那个
    pnputil /add-driver <备份目录>\hdxmsi.inf /install
· 备份驱动（改之前一定做）：
    pnputil /export-driver <oem编号>.inf <备份目录>
```

**方案见 `pnputil /enum-drivers` 看全部驱动包**（`oemNN.inf`）。

**⚠️ 一个真实的副作用**：重装 Realtek 驱动后，
**模拟输出端点（"扬声器"）可能仍然不出现** ——
某些版本的 Realtek 驱动需要配套的 UWP 应用（如 Realtek Audio Console）才有模拟端点。
这时可用的是 HDMI / 显示器扬声器。

## 15. 系统还原点建不了（`提供程序加载失败`）

**现象**：
```
Enable-ComputerRestore  -> Provider load failure
Checkpoint-Computer     -> 提供程序加载失败
```

**根因**：**系统还原服务 `SDRSVC` 不存在**（`Get-Service SDRSVC` 查不到）。
`VSS` 和 `swprv` 都在跑，缺的正是它。

**替代的"护身符"**（改驱动/系统设置前做）：

```powershell
# 导出驱动包备份
pnputil /export-driver oem55.inf <FAIRY_ROOT>\backup\drivers
# 导出音频相关注册表
reg export "HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\MMDevices\Audio" <FAIRY_ROOT>\backup\audio.reg /y
```

**实测**：驱动备份比还原点**更快、更对症**（还原点恢复整机，驱动备份只回滚驱动）。

## 16. 音乐被永久压低了，恢复不回来

**现象**：让位（ducking）之后，音乐音量一直很小，越用越小。

**根因（历史 bug，已修）**：
```
duck() 会把"当前音量"存成令牌，unduck() 用它恢复。
但如果进程死在"已压低"的中间态，下次 duck() 会把【已经压低的值】当成"原值"存下来
-> 音量阶梯式永久下降，用户会以为音箱坏了
```

**已做的修复**：
- `volume_duck.py` 写令牌改成**原子写**（`.tmp` + `os.replace`）
- 原来的 `except: pass` 改成**必须出声**（写失败会静默丢令牌，与"永久卡低"叠加且无从排查）
- `fairy_ball.py` 的 `_worker` 线程启动时做**上电自愈**（`emergency_restore()`）

**如果还是卡住了**：重启球，它会自愈。

**策略位置**：**已内置在代码里**（`media_duck.py` / `volume_duck.py`）。历史上的 `audio_policy.json` 已于 2026-10-11 删除 —— 它是死配置（全项目零读取点），改它不生效。

## 18. 球偶尔报 `main thread is not in main loop`

**现象**：
```
[fairy] _on_state(doing) 处理失败: main thread is not in main loop
RuntimeError: main thread is not in main loop
```
位置：`_on_state` 里调 `self.after(0, lambda: self._bubble(...))`。

**根因**：`_on_state` 跑在**后台线程**，却直接调了 Tk 的 `after()` ——
**Tk 不允许在非主线程 / 主循环启动前这么调。**

**影响**：**那一条气泡丢失了**（不会崩，外面有 try 兜住并打印）。
**属于既有问题**，尚未修复。

## 20. 开源版缺外观素材会怎样（已内置占位回退）

**现象（旧版本）**：clone 下开源包跑球，球起不来 —— `FileNotFoundError`。

**根因（已核实代码）**：
```
fairy_ball.py:47    ASSETS = r"<FAIRY_ROOT>\assets\ball_128"    <- 硬编码
fairy_ball.py:468   def load_frames(...): files = os.listdir(ASSETS) ...
fairy_ball.py:1105  self.files, ... = load_frames()            <- 在 __init__ 内
-> 旧版：目录不存在 = 抛 FileNotFoundError = 球启动即崩
```

**★ 已修复（2026-10-09 起）—— 现在有占位回退**：
```
load_frames() 现在：
  · os.listdir 包 try/except   -> 目录不存在也不抛
  · 逐帧 Image.open 包 try     -> 坏帧跳过并打警告
  · 一帧都没有 -> 自动用【占位外观】（透明底 + 居中浅蓝圆）继续运行
  · 返回签名不变，调用方零改动
实测：真实素材=122 帧（行为不变）· 目录不存在=占位不崩 · 目录空=占位不崩
```

**所以现象变成了**：**球起得来，但显示成一个纯色圆**，日志里有醒目警告。

**解法**：往 `<FAIRY_ROOT>\assets\ball_128\` 放你自己的 128×128 带透明通道 PNG
（见 [`README.md`](README.md) 的「外观素材也需要自备」一节）。
**路径写死在代码里，换目录要改 `fairy_ball.py` 第 47 行。**

## 附：一般性排障原则

1. **先确认"有没有程序在干这件事"** —— 大量"没反应"其实是"没在跑"。
2. **关键路径必须有日志** —— 没有日志的"看着像死了"是最难查的。
   （而且如果进程用 `pythonw` 跑，`print` 会被丢弃 —— 要重定向。）
3. **别用关键字搜，用指纹搜** —— 比如 Edge 的指纹是 `.mp3` 扩展名，不是 "edge" 字样。
4. **别只信名字** —— 设备名里有"麦克风"不代表能打开。
5. **易变事实先验再用** —— 版本、开关、模型行为都会变。
6. **改危险的东西之前先备份** —— 驱动、注册表、代码，都留 `*.bak_before_*`。
